- **基线**：`commit c2d55a6` (master), `VERSION 0.1.0`

### 核心风险速览
1. **A3-001 [High - 架构倒灌]** `src/protocol/policy.c` 包含 `mcpkit/server/session.h`，协议层向上反向依赖服务端会话层。
2. **A3-002 [High - 内存安全/契约]** `src/core/auth.c` 的 Base64 解码硬编码 libc `malloc()` 绕过上下文分配器，且与 `encode` 释放规则不匹配，兼有领域泄漏（强行绑定 `mcp_oauth_free_string`）与返回裸 `int` 问题。
3. **A3-003 [Medium - 复杂度]** `src/core/auth.c` 膨胀至 1539 行，成为全仓第一大文件，堆叠了 6 项 RFC/SEP 规范，呈现出早期 `dispatcher.c` 的 God-File 膨胀趋势。
4. **A3-004 [Medium - 编译告警]** `-O3` 优化下 `src/transport/streamable_http.c` 在 3 处触发 `-Wformat-truncation` 告警。
5. **A3-005 [Low - 人机工学]** 缺乏 `mcp_tool_result_text` 级便捷构造器，示例代码与新手接入体验存在严重的样板代码负担。

## §4 架构与分层严谨性深度审查

项目架构设计的核心红线是：
`Examples -> apps -> server/client -> protocol -> core`
`core` 与 `protocol` 必须保持标准 C23/libc 零依赖，禁止向上依赖或引入外部重型网络/加密库。

### 4.1 优秀实践确认
- **零外部库污染**：`grep` 验证确认 `src/core/` 与 `src/protocol/` 中未包含任何 OpenSSL、libuv、curl 或 pthread 头文件（采用原生 C23 `<threads.h>` / `<stdatomic.h>` 与内建 SHA-1/SHA-256）。
- **服务端分发解耦成功**：原 1652 行的巨型文件 `src/server/dispatcher.c` 已成功拆解为 `dispatcher.c`（256 行调度）、`queue.c`（160 行队列）、`routes.c`（1471 行路由）、`session.c`（338 行会话）及统一的方法表 `src/method_table.h`，模块间通过内部头文件通信，结构大幅改善。

### 4.2 发现的问题
#### A3-001 [High] 协议层向上反向依赖服务端层 (`protocol` → `server`)
- **源码位置**：
  - `include/mcpkit/protocol/policy.h:22, 36, 49`
  - `src/protocol/policy.c:12, 16-35`
- **问题细节**：
  `src/protocol/policy.c` 第 12 行直接包含了服务端专有头文件：
  ```c
  #include "mcpkit/server/session.h"
  ```
  其公开 API 签名直接要求传入 `const mcp_session_t *session`，并在内部调用 `mcp_session_negotiated(ctx, session)` 来判断协议版本。
- **危害**：
  违背了分层单向流动原则（`server -> protocol -> core`）。`session` 概念属于有状态的服务端会话管理，协议策略层本应只关注纯粹的协议语义与版本枚举（`mcp_proto_version_t`）。若客户端或其他无 session 的环境需要查询协议策略，将被迫引入服务端依赖。
- **整改建议**：
  将 `mcp_proto_policy_*` 的入参重构为纯协议版本 `mcp_proto_version_t version`：
  ```c
  bool mcp_proto_policy_method_deprecated(mcp_context_t *ctx,
                                          mcp_proto_version_t proto_version,
                                          const char *method);
  ```
  在服务端路由调用处（`routes.c`），由服务端直接传递 `mcp_session_negotiated(ctx, session)`。彻底移除 `protocol` 对 `server/session.h` 的 `#include`。

#### A3-003 [Medium] 认证模块 `src/core/auth.c` 出现新的 God-File 膨胀趋势
- **源码位置**：`src/core/auth.c`（1539 行，全仓第一大源码文件）
- **问题细节**：
  在历次安全扩展中，`auth.c` 集中堆叠了：
  1. SHA-256 原生哈希引擎与 Base64URL 辅助编解码；
  2. 标准 Base64 编解码与 SEP-2243 Sentinel 哨兵解析；
  3. RFC 7636 PKCE S256 Challenge 计算与生成；
  4. RFC 9728 受保护资源元数据解析与序列化；
  5. RFC 8414 / RFC 9728 AS 授权服务器探测与发现合并；
  6. RFC 6749 / RFC 7591 客户端凭据与客户端动态元数据（DCR）解析验证；
  7. RFC 8693 OAuth 2.0 令牌交换请求构建与响应解析。
- **危害**：
  文件职责过多、内聚度下降，修改任意认证协议均在该单文件中产生冲突，重现了此前 `dispatcher.c` 膨胀的历史轨迹。
- **整改建议**：
  在 `src/core/auth/` 目录下按 RFC 维度进行拆分，如 `auth_pkce.c`、`auth_discovery.c`、`auth_token_exchange.c`、`auth_client.c`，主头文件保持统一门面。

## §5 内存安全、所有权与并发模型审查

### 5.1 异步网络与并发控制（强项）
- **连接生命周期**：`src/transport/async_server.c` 严格采用基于原子操作的引用计数机制（`conn_ref` / `conn_unref`）。
- **优雅与突发关闭**：`conn_detach_and_close()` 使用 `atomic_exchange(&conn->detached, true)` 实现严格幂等的连接脱钩，在 Reactor 移除、套接字关闭及会话清理时无悬垂风险。
- **写队列防悬垂**：工作线程异步排队响应时通过 `conn_ref(conn)` 锁定连接，在 `task_complete` 中平衡 `conn_unref`，ASan 压力测试下零竞态泄漏。
- **Reactor 多路复用**：`src/runtime/reactor.c` 对 Linux `epoll` 与 POSIX `poll` 双引擎在重入添加/删除描述符时维护快照列表，规避迭代器失效。

### 5.2 发现的问题
#### A3-002 [High] Base64 编解码器内存分配器绕过、释放规则不匹配与领域泄漏
- **源码位置**：
  - `src/core/auth.c:186-271`
  - `include/mcpkit/core/auth.h:488-521`
- **问题细节**：
  在 P4-a 扩展引入的标准 Base64 编解码器中，存在多重契约不一致：
  1. **绕过上下文分配器**：
     `mcp_base64_encode()` 严格使用 `alloc_of(ctx)->malloc_fn` 分配；但 `mcp_base64_decode()` 却完全忽略 `ctx`（代码显式写着 `(void)ctx;`），直接调用 libc 原生 `malloc()`：
     ```c
     // src/core/auth.c:268
     uint8_t *out_buf = (uint8_t *)malloc(byte_len);
     ```
     如果用户在 `mcp_context_t` 中注入了自定义内存池或跟踪分配器，解码器将完全脱管；
  2. **释放规则矛盾与非对称**：
     头文件与实现注释中写道：
     `encode allocates via ctx allocator (free with mcp_oauth_free_string); decode allocates via libc malloc (free with free).`
     这使得调用方必须牢记“编码用 oauth 函数释放，解码用原生 free 释放”，极易引发配对错误；
  3. **领域泄漏（Domain Leakage）**：
     通用 Base64 编码字符串的释放竟然绑定在 `mcp_oauth_free_string()` 上！Base64 是通用数据表示，与 OAuth 领域无本质从属关系；
  4. **错误码契约违规**：
     `mcp_base64_decode()` 声明为：
     ```c
     int mcp_base64_decode(mcp_context_t *ctx, const char *in, size_t in_len,
                           uint8_t **out, size_t *out_len);
     ```
     失败时返回 bare `int`（`-1`），违背了 SDK 统一返回 `mcp_status_t` 的铁律。
- **整改建议**：
  1. **补充核心公共释放接口**：在 `include/mcpkit/core/context.h` 中正式引入通用公共释放函数：
     ```c
     void mcp_free(mcp_context_t *ctx, void *ptr);
     ```
     底层统一委派给 `alloc_of(ctx)->free_fn(ptr, alloc->userdata)`，彻底填补公共头文件中缺失通用内存释放接口的根本空白。
  2. **提取独立 Base64 工具模块**：将 Base64 从 `auth.c` 剥离为通用工具（如 `src/core/base64.c`）；
  3. **遵从上下文分配器与统一状态码**：`mcp_base64_decode` 必须使用 `alloc_of(ctx)->malloc_fn`，返回值统一改为 `mcp_status_t`；
  4. **统一释放语义**：Base64 编解码产物与通用字符串统一使用 `mcp_free(ctx, ptr)` 释放，解除对 OAuth 专属清理函数的倒灌依赖，并同步修正 `include/mcpkit/core/auth.h:537` 中 `mcp_http_fetch_fn` 的释放契约，根除 libc `malloc` 与自定义内存池混用的 UB 隐患。

## §6 易用性与 API 人机工学评估

### 6.1 优秀体验
- **错误码与上下文一致性**：除上述 `mcp_base64_decode` 外，所有可失败的公开 API 均统一返回 `mcp_status_t`。
- **首参规范**：所有具备上下文状态的 API 均将 `mcp_context_t *ctx` 作为第一个参数，且底层统一支持 `ctx == NULL` 时自动回退至 libc 默认分配器与日志器，极大地降低了轻量级场景的初始化门槛。

### 6.2 发现的问题
#### A3-005 [Low] 缺乏顶层结果构造便捷函数，导致示例与用户代码样板膨胀
- **源码位置**：`examples/minimal-server/main.c:20-60`
- **问题细节**：
  在 MCP 协议最常见的场景中，工具（Tools）执行后仅需返回简单的文本结果（`{"content":[{"type":"text","text":"..."}]}`）。
  但在当前 SDK 下，开发者必须手动编写 40 余行代码，连续调用 `mcp_json_object_new`、`mcp_json_string_new`、`mcp_json_array_new`、`mcp_json_array_append`，并处理多达 7 处嵌套回滚 `mcp_json_destroy`（即使已有 `mcp_content_text_new_annotated`，也没有直接产出 ToolResult 容器的封装）。
- **危害**：
  极大地增加了外部 C 开发者接入 `mcpkit-c` 的心智负担与内存泄漏几率，使“极简示例”显得沉重且不友好。
- **整改建议**：
  在 `include/mcpkit/protocol/message.h` 或 `server.h` 中提供高层快捷函数：
  ```c
  mcp_json_value_t *mcp_tool_result_text_new(mcp_context_t *ctx, const char *text);
  mcp_json_value_t *mcp_tool_result_error_new(mcp_context_t *ctx, const char *error_msg);
  ```
  一键生成标准的 MCP Tool Result 对象，让最基础的工具处理函数缩减至 3~5 行。

## §7 工程基线与文档一致性审查

#### A3-004 [Medium] `-O3` 编译优化下触发 `-Wformat-truncation` 告警
- **源码位置**：`src/transport/streamable_http.c:527, 539, 546`
- **问题细节**：
  GCC 在 `-O3` 内联优化函数 `xmcp_check_headers` 时发现：
  ```c
  snprintf(err_param, err_cap, "%s", anno->param_name);
  ```
  `anno->param_name` 的源缓冲区理论上限为 4223 字节，而目的缓冲区 `err_param` 固定为 64 字节，编译器提示字符串可能发生截断。
- **危害**：
  破坏了项目“零编译告警通过”的工程质量目标。
- **整改建议**：
  显式截断保护或增加边界断言，亦或动态按需分配错误提示字段。

#### A3-006 [Low] README 构建选项表遗漏新增选项
- **源码位置**：`README.md:60-72` vs `cmake/MCPKitOptions.cmake`
- **问题细节**：
  `cmake/MCPKitOptions.cmake` 中已包含 `MCPKIT_BUILD_TLS`（TLS 适配层）与 `MCPKIT_REACTOR_FORCE_POLL`（Reactor 强制 Poll 后端），但 `README.md` 的构建选项表格中尚未收录这两项。
- **整改建议**：
  在 `README.md` 的构建选项表中补齐这两项的默认值及说明。

#### A3-007 [Info] 顶层总头文件 `mcpkit.h` 未在模块参考手册中列出
- **源码位置**：`include/mcpkit/mcpkit.h` vs `docs/module-reference.md`
- **问题细节**：
  `include/mcpkit/` 下的全部 38 个子模块头文件在 `docs/module-reference.md` 中均有详尽的章节记载，但对外最常用的统一入口头文件 `mcpkit.h` 自身没有专节描述。
- **整改建议**：
  在 `docs/module-reference.md` 开篇补充 `mcpkit.h` 聚合头文件的包含范式说明。

## §8 优先级整改路线图 (Prioritized Remediation Roadmap)

根据对系统稳定性、架构纯洁性与开发者体验的影响，制定以下四级整改路线图：
