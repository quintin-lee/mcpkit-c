# mcpkit-c 全面体检报告 — 2026-10-09

基线：`HEAD 21fd21`（master），`VERSION 0.1.0`。本报告所有结论均有命令输出支撑，
复核对象包括 2026-09-17 审计报告（基线 `a5fd2b5`）的全部结论在当前 HEAD 是否成立。

## §1 方法

评估了三种做法：(a) 分层自下而上通读、(b) 风险导向复现审计问题、
(c) 以 9-17 审计报告为基线做增量复核。实际采用 **(b)+(c) 组合**：
先复核审计结论在当前 HEAD 是否成立，再跑实证 gate 用数据说话。

## §2 项目速览

零依赖 C23 MCP SDK + runtime：
core / json / protocol / server / client / transport / runtime / apps / plugin，
约 40 个源文件。

自 9-17 审计基线后的新增协议扩展：MRTR 多轮请求、Tasks（SEP-2663）、
Skills（SEP-2640）、Content Annotations、Sampling Tools、URI Template Level 4、
OAuth PKCE + RFC 8693 Token Exchange、SSE 解析器、Registry Manifest + CLI 配套命令。
测试从 33 个涨到 **56 个（默认）/ 59 个（HTTP 开启）**，
examples 从 9 个涨到 **10 个**（新增 `mrtr-server`）。

## §3 架构评价（项目最强项，依然成立）

分层纪律（`apps → server/client → protocol → core`）、所有权转移规则、
`mcp_status_t` 统一错误码、ops 表插件缝——抽查的头文件注释与实现一致，
原则没有被新功能冲垮。新增扩展（tasks/skills/content/sampling）都是挂在
protocol 层的新模块，没有回灌依赖。

## §6 新观察到的风险（审计基线之后产生）

1. **`src/server/dispatcher.c` 膨胀到 1652 行（65KB），全仓最大文件**
   （第二名 `src/core/auth.c` 1027 行）。路由、校验、订阅、高级方法全塞一起，
   已出现 god-file 征兆，后续改动冲突面大，建议拆分评估。
2. **默认-allow 权限模型**（审计 A-023 仍在）：新 session 默认
   `granted = 0xFFFFFFFF`，所有 tool 默认可调。在 tool visibility /
   permission mask 能力越加越多的今天，这个默认值的安全含义应在架构文档里
   明确一句话，否则新接入者会误以为是默认拒绝。
3. **`-Wall -Wextra` 未进构建系统**：§4 证明当前代码能零警告通过，
   此时接入成本极低（加两行 `add_compile_options`），越晚加越贵。
