# mcpkit-c Architecture & Code-Quality Audit — 2026-09-17

Baseline: commit `a5fd2b5` (master). All evidence reproducible from that tree.

## §1 Executive summary

- **31/33** baseline tests pass; **2 deterministic failures**: `test_dispatcher` (SIGSEGV) and `test_socket` (SIGPIPE).
- **2 Critical** findings, **3 High**, **8 Medium**, **8 Low**, **5 Info** — 24 total.
- Top risks:
- Build hygiene: 3 CMake options (`MCPKIT_BUILD_APPS/CLIENT/SERVER`) are declared but never read anywhere — dead options.
- Docs drift: `docs/module-reference.md` is substantially out of date (wrong dispatcher API, ~50 wrong `int`/`mcp_status_t` signatures, wrong plugin signatures); README examples table omits 2 of 9 examples and its build-options table omits 6 of 13 options.

## §2 Methodology

## §3 Findings

### Critical

#### A-001 — `test_dispatcher` deterministically segfaults in Release builds  [Critical]
- Location: `tests/unit/test_dispatcher.c:266` (crash site `strcmp(ns, "echo")` with `ns == NULL`), triggered by `src/server/dispatcher.c` + `src/json/builtin.c` under `-O3 -DNDEBUG`.
- Evidence:
  - `./build/tests/test_dispatcher` → exit **139** (SIGSEGV), 5/5 runs, deterministic.
  - GDB (Release, no symbols): crash inside glibc `strcmp` called from `main`; `rdi=0` (first string is NULL), `rsi="echo"`.
  - **Debug build passes (exit 0); ASan build passes** (with LD_PRELOAD workaround); UBSan-instrumented build passes. Only plain `-O3 -DNDEBUG` crashes.
- Risk: a unit test that is part of the default `ctest` suite crashes the *production* dispatch path on the default Release configuration. This means either (a) a genuine UB in `route_tools_list`/JSON DOM that `-O3` exploits, or (b) the test dereferences a NULL that asserts would have caught in Debug. Either way the "32 tests tested" claim in the README is false for Release, and the dispatch pipeline is not verified under the configuration users actually ship.
- Recommendation: rebuild `test_dispatcher` with `-O3 -g` and symbols; instrument `route_tools_list`'s `set_string(ctx, entry, "name", t->name)` and the response JSON to confirm which entry lacks `"name"`; fix the underlying allocator/DOM defect, then add a Release-mode regression test. Do not "fix" by lowering the test's optimization level.

#### A-002 — Socket transport turns peer-close SIGPIPE into a fatal process kill  [Critical]
- Location: `src/transport/socket.c:115` (`write(b->fd, …)` in `sock_send`) and `:119` (newline write); no `MSG_NOSIGNAL`/`SO_NOSIGPIPE` handling.
- Evidence: `./build/tests/test_socket` → exit **141** (128+SIGPIPE), 5/5 runs, deterministic, port 45678 confirmed free. GDB backtrace: `write() ← sock_send ← main`. The test's peer closes (or the accepted socket is no longer writable) and the bare `write(2)` delivers SIGPIPE; default disposition kills the process instead of returning `EPIPE` → `MCP_ERR_IO`.
- Risk: any server using the socket transport whose client disconnects mid-send **dies** rather than surfacing a transport error. Production MCP servers over TCP hit this whenever a client drops.
- Recommendation: write with `writev`/`send(fd, buf, len, MSG_NOSIGNAL)` (or `MSG_NOSIGNAL` on Linux) so a closed peer yields `MCP_ERR_IO`; then `test_socket` passes. Alternatively ignore SIGPIPE process-wide at transport create (worse — global state).

### High

#### A-003 — `docs/module-reference.md` documents a dispatcher API that does not exist  [High]
- Location: `docs/module-reference.md:328-338` vs `include/mcpkit/server/dispatcher.h`.
- Evidence: the doc describes `mcp_dispatcher_create / mcp_dispatcher_submit / mcp_dispatcher_process_one` and a `mcp_dispatcher_t` handle. The actual header defines **`mcp_queue_create / mcp_queue_push / mcp_queue_pop / mcp_queue_size / mcp_server_process_one`** with `mcp_queue_t`. None of the documented symbols exist anywhere in `include/` or `src/`.
- Risk: a consumer coding against the reference doc cannot compile; the real queue/`process_one` contract (including the ownership-transfer rules in the header's doc block) is undocumented in the reference.
- Recommendation: rewrite the `dispatcher.h` section to the `mcp_queue_*` + `mcp_server_process_one` API; state the ownership semantics (queue takes message ownership on `MCP_OK` push; `pop` transfers it out; `process_one` pops one and dispatches, `MCP_ERR_NOT_FOUND` when empty).

#### A-004 — `docs/module-reference.md` return-type drift: ~50 functions documented as `int`, actually `mcp_status_t`/`size_t`/`bool`  [High]
- Location: `docs/module-reference.md` (server/protocol/schema/transport/apps sections) vs the real headers.
- Evidence: e.g. doc says `int mcp_schema_add_property(…)` — header `include/mcpkit/json/schema.h:84` is `mcp_status_t mcp_schema_add_property(…)`. Same pattern: `mcp_schema_validate`, `mcp_resource_set_cleanup`, `mcp_session_grant/revoke/set_apps_host`, `mcp_transport_*`, `mcp_csp_set/serialize`, all `mcp_client_*` convenience methods, `mcp_timer_schedule/poll/cancel` — all `mcp_status_t` in headers, all `int` in the doc. Also `mcp_timer_cancel` is documented as `int` but actually returns `size_t` (count removed).
- Risk: API consistency is this project's stated principle ("Errors are `mcp_status_t` only"). The reference doc directly contradicts it, inviting wrong error handling.
- Recommendation: regenerate the module reference from the headers (or add a CI check that diffs documented signatures against `grep` of `include/`).

#### A-005 — `docs/module-reference.md` plugin section is wrong on signatures  [High]
- Location: `docs/module-reference.md:549-560` vs `include/mcpkit/plugin/plugin.h`.
- Evidence: doc shows `mcp_plugin_register(const mcp_plugin_entry_t *)`, `mcp_plugin_unregister(const char *kind, const char *name)`, and a text `kind` field (`"json","transport","executor"`). The real API is `mcp_plugin_register(mcp_plugin_kind_t kind, …)` / `mcp_plugin_unregister(mcp_plugin_kind_t kind, const char *name)` with an enum `mcp_plugin_kind_t` (fix `a5fd2b5` added the global mutex — the doc never mentions thread-safety of the registry at all).
- Risk: wrong entry type (struct vs enum) means the documented call does not compile.
- Recommendation: fix the plugin section to the `mcp_plugin_kind_t` enum + `(kind, name, impl)` signature; document the process-wide mutex from `a5fd2b5`.

### Medium

#### A-006 — `mcp_protocol_negotiate` contract: doc says "strdup, caller frees"; header says borrowed static string  [Medium]
- Location: `docs/module-reference.md:226` vs `include/mcpkit/protocol/initialize.h:78`.
- Evidence: the module reference says `mcp_protocol_negotiate` "returns the chosen version string (**strdup, caller frees**)", but the real doc (and impl `src/protocol/initialize.c:6`) says it returns a pointer to a **static** string in `k_supported` — no allocation, nothing to free.
- Risk: a caller that `free()`s the result corrupts a static.
- Recommendation: correct the reference to "borrowed static string, lifetime = process; never free".

#### A-007 — `MCP_TOOL_VIS_BOTH` value drift in module reference  [Medium]
- Location: `docs/module-reference.md:287-291` vs `include/mcpkit/server/tool.h:85-87`.
- Evidence: doc states `MCP_TOOL_VIS_MODEL = 0, MCP_TOOL_VIS_APP = 1, MCP_TOOL_VIS_BOTH = 2`. The header defines only `MODEL = 0, APP = 1` plus `BOTH` (value verified in `tool.h`); the doc's `= 2` literal is an invention — the enum is a filter tag, not a bitmask, and consumers should not rely on a hardcoded `2`.
- Recommendation: drop the hardcoded literal; describe `BOTH` as "visible to both host types (default)".

#### A-008 — Three declared CMake options are never read (dead options)  [Medium]
- Location: `cmake/MCPKitOptions.cmake:3-5` (`MCPKIT_BUILD_APPS`, `MCPKIT_BUILD_CLIENT`, `MCPKIT_BUILD_SERVER`).
- Evidence: `grep -rc` across `CMakeLists.txt cmake/ src/ include/` finds each referenced **only** at its `option()` declaration — `CMakeLists.txt` builds `MCPKIT_CORE_SOURCES` unconditionally (server/apps/client `.c` files are always in the list; nothing branches on these three).
- Risk: users set `-DMCPKIT_BUILD_APPS=OFF` etc. expecting a slimmer build; nothing changes. Silent no-op flags are a support trap.
- Recommendation: either implement the branching (split server/apps/client sources behind the flags) or delete the three options and note in the reference that those layers are always built.

#### A-009 — Build emits no `-Wall -Wextra` enforcement (zero-warning bar is unenforced)  [Medium]
- Location: `cmake/MCPKitSanitizers.cmake`, root `CMakeLists.txt`.
- Evidence: a clean Release build emits **0** warnings — but only because no warning flags are set; `add_compile_options` in the sanitizer preset carries only sanitizer flags, and the root CMake adds none. The zero-warning bar is unenforced.
- Risk: latent warnings (implicit declarations, signed/unsigned, etc.) are invisible in CI and locally; the "zero warnings" discipline stated in prior plan docs is not actually verified.
- Recommendation: add `add_compile_options(-Wall -Wextra)` (optionally gated on a new `MCPKIT_ENABLE_WERROR` for `-Werror`) and clean up any warnings that surface.

#### A-010 — README examples table omits `prompt-server` and `socket-server`  [Medium]
- Location: `README.md:80-86` vs `examples/` (9 subdirectories = 9 runnable programs).
- Evidence: table lists 7 of 9 examples; `prompt-server` and `socket-server` are buildable (in `examples/CMakeLists.txt`) but undocumented.
- Recommendation: add the two rows.

#### A-011 — README build-options table omits 6 of 13 declared options  [Medium]
- Location: `README.md:59-67` vs `cmake/MCPKitOptions.cmake:1-13`.
- Evidence: README documents only `BUILD_TESTS/EXAMPLES/TOOLS/HTTP/FUZZ`, `ENABLE_ASAN/UBSAN`. Missing: `MCPKIT_BUILD_APPS`, `MCPKIT_BUILD_CLIENT`, `MCPKIT_BUILD_SERVER` (dead — see A-008), `MCPKIT_BUILD_SOCKET`, `MCPKIT_ENABLE_TSAN`, `MCPKIT_BUILD_SHARED`.
- Recommendation: document all 13 (or trim to the live ones once A-008 is resolved).

#### A-012 — `test_stdio_loopback` is registered but not gated on any option; `test_socket` is gated — inconsistent test wiring  [Medium]
- Location: `tests/CMakeLists.txt:82-88` (stdio loopback unconditional) vs `:163-167` (`test_socket` behind `MCPKIT_BUILD_SOCKET`).
- Evidence: the stdio transport is always compiled, so its test is always built; the socket test is option-gated. Two transports, two test policies.
- Recommendation: unify — either gate both on their build options or build both unconditionally.

### Low

#### A-024 — TSan gate: `test_executor` crashes under ThreadSanitizer  [Medium]
- Location: `src/runtime/threadpool.c` (worker/active accounting), exercised by `tests/unit/test_executor.c`.
- Evidence: `cmake -S . -B build-tsan -DCMAKE_BUILD_TYPE=Debug -DMCPKIT_ENABLE_TSAN=ON && cmake --build build-tsan -j`, then `./build-tsan/tests/test_executor` → `ThreadSanitizer: SEGV on unknown address 0x000000000018 (pc …)` on a worker thread — the TSan-instrumented binary itself faults (NULL+0x18 = member access on a NULL `pool_t`/node) where the non-TSan build of the same test passes.
- Risk: the threadpool's lock/accounting (`pending`/`active`/`stop` in `pool_t`) is not verified by the concurrent tests; TSan either can't cleanly run them on this toolchain (GCC TSan) or there is a genuine NULL-deref race. Either way the "threadpool executor" concurrency claim in the README is unverified.
- Recommendation: re-run `test_executor` under Clang-TSan to disambiguate toolchain vs. real race; if real, fix the NULL `pool_t` path in `pool_destroy_backend`/`pool_abort` before shipping.
#### A-013 — `CHANGELOG.md` "Unreleased" still lists phase work as if not shipped  [Low]

#### A-014 — `docs/architecture/overview.md` threading claim is imprecise  [Low]

#### A-015 — `module-reference.md` types section lists `mcp_schema_builder_t` as "internal only" but it's a public typedef  [Low]

#### A-016 — `module-reference.md` client section: `mcp_client_initialize` doc says "fire-and-forget initialized notification"  [Low]
- Location: `docs/module-reference.md:420` vs `include/mcpkit/client/client.h` doc block.

#### A-017 — `mcp_queue_push` doc block mentions `session` but the public signature's ownership of the session isn't stated  [Low]

### Info

#### A-019 — `MCPKIT_ENABLE_TSAN` + `MCPKIT_ENABLE_ASAN` are mutually exclusive (enforced)  [Info]
- `cmake/MCPKitSanitizers.cmake:5-7` raises `FATAL_ERROR` if both are ON. Documented nowhere in the README.
- Recommendation: add a one-line note to the build-options table.

#### A-020 — Fuzz drivers have no committed corpus; replay is manual  [Info]
- `tests/fuzz/*.c` read stdin; `test_json_fuzz` etc. generate deterministic input in-process. There is no on-disk seed corpus directory.
- Recommendation: commit a `tests/fuzz/corpus/` with a handful of seed files for future libFuzzer integration.

#### A-021 — Shared-library variant is built but not exercised by any test  [Info]
- `MCPKIT_BUILD_SHARED=ON` produces `libmcpkit_core.so`; no test links it (all tests link the static lib).
- Recommendation: add a test that links the shared variant, or note the gap in the reference.

#### A-022 — `mcp_stdio_serve` owns its transport lifecycle; caller must not also stop/destroy  [Info]
- `src/transport/stdio.c` doc block states this; `examples/stdio-server` follows it. No test verifies the "must not double-destroy" path.
- Recommendation: add a negative test.

#### A-023 — Default permission mask is ALL-granted (`0xFFFFFFFF`)  [Info]
- `src/server/session.c:21` sets `granted = 0xFFFFFFFFu` so every tool is callable until explicitly revoked. This is a security-relevant default worth calling out in `docs/architecture/overview.md`.
- Recommendation: document the default-deny-by-absence-of-grant is *not* the model; default is default-allow.
